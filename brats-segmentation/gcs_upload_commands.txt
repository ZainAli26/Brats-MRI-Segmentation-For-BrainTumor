GCS — upload the BraTS training data to a bucket: commands
Run all of these from brats-segmentation/ (paths are ../Brats2024/... as in exp27_commands.txt).

Environment as of 2026-08-11:
  gcloud + gsutil installed (/snap/bin), authenticated against the GCP project below.
  Substitute your own values for <your-project> and <your-bucket> throughout, or export
  them once:  export PROJECT=...  BUCKET=gs://...
  No BraTS bucket existed yet at that point; one was created per section 0.

What needs to move (~88 GB, ~18.5k files):

  ../Brats2024/training_data1_v2          43 GB    8,100 files
  ../Brats2024/synthetic_regaug           39 GB    8,808 files    (exp27 only)
  ../Brats2024/training_data_additional  6.4 GB    1,626 files

Uploaded later, separately (see section 1 option C):

  ../Brats2024/validation_data           6.1 GB      940 files    official, unlabelled

Use `gcloud storage`, not `gsutil`. It parallelizes by default and is several times
faster; gsutil is in maintenance mode. Do not add `-m` — that is a gsutil flag.

-------------------------------------------------------------------------------
0. ONE-TIME SETUP
-------------------------------------------------------------------------------

gcloud config set project <your-project>
export BUCKET=gs://<your-bucket>        # bucket names are GLOBALLY unique — change if taken

Location: pick the single region closest to wherever the GPU is rented, not multi-region
(multi-region costs ~25% more to store and buys nothing here).

gcloud storage buckets create $BUCKET \
    --location=us-central1 \
    --default-storage-class=STANDARD \
    --uniform-bucket-level-access

Deliberately NOT enabling object versioning: every overwrite would silently keep the old
copy and double the bill on 88 GB.

-------------------------------------------------------------------------------
1. UPLOAD — option A: directory copy (browsable, selective)
-------------------------------------------------------------------------------
Keeps one object per NIfTI, so you can pull a single patient or just the real data.
Costs per-object overhead on 18.5k files at both ends.

gcloud storage cp -r ../Brats2024/training_data1_v2        $BUCKET/Brats2024/
gcloud storage cp -r ../Brats2024/training_data_additional $BUCKET/Brats2024/
gcloud storage cp -r ../Brats2024/synthetic_regaug         $BUCKET/Brats2024/

Interrupted? Re-run as rsync — it skips what already matches on size+mtime:

gcloud storage rsync -r ../Brats2024/training_data1_v2 $BUCKET/Brats2024/training_data1_v2

-------------------------------------------------------------------------------
1. UPLOAD — option B: tarballs (faster end to end; use this for a rented GPU box)
-------------------------------------------------------------------------------
The cloud box needs the whole directory anyway, and one large object streams at line rate
instead of paying a round trip per file. Streams straight through — no local temp copy,
so no extra disk needed (only ~140 GB was free on / as of 2026-08-11).

tar -cf - ../Brats2024/training_data1_v2        | gcloud storage cp - $BUCKET/tar/training_data1_v2.tar
tar -cf - ../Brats2024/training_data_additional | gcloud storage cp - $BUCKET/tar/training_data_additional.tar
tar -cf - ../Brats2024/synthetic_regaug         | gcloud storage cp - $BUCKET/tar/synthetic_regaug.tar

No `-z`. The payload is already .nii.gz; gzip would burn CPU for ~0% gain.
Caveat: a streamed upload cannot be resumed — a dropped connection restarts that tar.
On a flaky link prefer option A.

-------------------------------------------------------------------------------
1. UPLOAD — option C: the OFFICIAL validation set  (added 2026-08-25)
-------------------------------------------------------------------------------
Uploaded separately from the training data because it is needed for a different job:
producing portal submissions from a cloud box, not training. 188 cases / 940 files /
6.1 GB, INPUTS ONLY — there is no ground truth for it anywhere, so it cannot be scored
offline. Keep it mentally separate from the seed-42 held-out test set (153 cases WITH
labels, carved out of the *training* data); see the README object below.

gcloud storage rsync -r ../Brats2024/validation_data $BUCKET/Brats2024/validation_data

rsync, not `cp -r`: 940 objects, so a re-run after an interruption skips what already
matches instead of re-pushing 6.1 GB. Same prefix layout as the training dirs, so the
box ends up with `Brats2024/validation_data` exactly where `val_dir:` in the experiment
configs expects it.

Two small metadata objects sit at the prefix root alongside the case dirs:
  _README.md      what this set is, what it is not, and the `-sub` caveat
  _case_list.txt  the 188 case ids
`_collect_case_dirs()` matches on CASE_PATTERN, so these two are ignored by the loader
after a pull.

The `-sub.nii.gz` in each case dir is NOT from BraTS — it is the t1c-t1n subtraction
channel precomputed locally by precompute_subtraction.py, shipped so a 5-channel model
(exp23/exp26/exp27) can infer on the box without recomputing it. The 4 BraTS modalities
are byte-identical to the release.

-------------------------------------------------------------------------------
3. PULL ON THE GPU BOX
-------------------------------------------------------------------------------
Auth first. On a rented box do NOT paste your user credentials — mint a service account
key with objectViewer on this bucket only, or use a short-lived access token.

  gcloud auth activate-service-account --key-file=key.json
  # or, no gcloud install on the box, token minted locally and valid ~1 h:
  #   curl -H "Authorization: Bearer $(gcloud auth print-access-token)" \
  #        -o data.tar "https://storage.googleapis.com/storage/v1/b/BUCKET/o/OBJECT?alt=media"

From tarballs (see gcs_download_commands.txt for the full pull procedure):
gcloud storage cat $BUCKET/tar/training_data1_v2.tar | tar -xf - -C /workspace

tar stripped the leading `../` at creation, so members are already Brats2024/<dataset>/...
Extract into the PARENT (/workspace), not /workspace/Brats2024, or you get Brats2024/Brats2024/.

From directories:
gcloud storage rsync -r $BUCKET/Brats2024/training_data1_v2 /workspace/Brats2024/training_data1_v2

Then preprocess ON the cloud box (CPU is cheap while the GPU idles) rather than uploading
the ~34 GB cache too.

-------------------------------------------------------------------------------
4. COSTS — read before pushing 88 GB
-------------------------------------------------------------------------------
Upload/ingress                free
Storage, 88 GB STANDARD       ~$1.80 / month
Egress GCS -> non-GCP box     ~$0.12/GB  =  ~$10.50 EVERY full pull, per box
Egress GCS -> GCP VM, same region   free

That egress is real against the ~$130 staged budget in the cloud plan, and it recurs for
each box rented. If you expect more than 2-3 RunPod/Vast boxes, keep the tarball on the
provider's own volume storage after the first pull instead of re-downloading from GCS.
If the training itself runs on a GCP VM, put it in us-central1 to match the bucket and
egress is free.

Do not leave 88 GB sitting there after the runs finish:

gcloud storage rm -r $BUCKET/Brats2024
gcloud storage rm -r $BUCKET/tar

Or set a lifecycle rule so it expires itself (90 days shown):

cat > /tmp/lifecycle.json <<'EOF'
{"rule":[{"action":{"type":"Delete"},"condition":{"age":90}}]}
EOF
gcloud storage buckets update $BUCKET --lifecycle-file=/tmp/lifecycle.json
